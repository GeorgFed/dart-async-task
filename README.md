# Dart: Future, Stream и сетевой репозиторий

Практика на 80 минут. Цель — написать сетевой слой и поработать с **реальным CoinGecko API**: список монет, детали, Stream, обновление цен и преобразование потока. Для **2 баллов** обязательны также поллинг, where/map и обработка ошибок.

## Начало работы

Нужен **Dart 3.9+**. Если установлен Flutter, используйте его Dart. Иначе установите [Dart SDK](https://dart.dev/get-dart). Откройте папку проекта в редакторе и выполните:

```bash
dart --version
dart pub get
```

В проекте только два Dart-файла. Редактируйте **lib/main.dart**: модели, интерфейс и готовый вывод уже есть. **test/test.dart** содержит все моки и проверки; студентам открывать или менять его не нужно.

Готовой реализации репозитория и сетевого помощника нет. Создайте свой класс с `implements CoinRepository`, который принимает `http.Client`, и верните экземпляр из `createRepository(client)`. Эта функция соединяет ваш класс с main и тестами, поэтому название класса можно выбрать самостоятельно. Сейчас она бросает UnimplementedError — до реализации это ожидаемо.

## Модели: всего шесть полей

| Модель | Поле Dart | Поле JSON |
|---|---|---|
| `Coin` | `id: String` | `id` |
| `Coin` | `name: String` | `name` |
| `Coin` | `priceUsd: double?` | `current_price` |
| `CoinDetails` | `name: String` | `name` |
| `CoinDetails` | `description: String` | `description.en` |
| `CoinDetails` | `changePercent: double?` | `market_data.price_change_percentage_24h` |

В `fromJson` только извлеките эти значения. Числа могут быть `int` или `double`: используйте `num` и `toDouble()`. Отсутствующая цена или процент становятся `null`, отсутствующее описание — `''`. Для обязательных имени/id можно считать, что API передаёт строки: отдельный валидатор схемы не нужен.

Список:

```json
[{"id":"bitcoin","name":"Bitcoin","current_price":65000}]
```

Детали:

```json
{"name":"Bitcoin","description":{"en":"Digital money"},"market_data":{"price_change_percentage_24h":2.5}}
```

## Реализуйте сетевой репозиторий

Базовый URL: `https://api.coingecko.com/api/v3/`. Делайте HTTP-запросы через **переданный** клиент, декодируйте JSON и создавайте модели. Не создавайте второй клиент внутри репозитория: тесты подставляют mock-клиент через createRepository.

| Метод | Контракт |
|---|---|
| `getTopCoins(limit)` | `/coins/markets`: `vs_currency=usd`, `order=market_cap_desc`, `per_page=limit`, `page=1`. При limit вне 1–250 — `ArgumentError` до запроса. Вернуть `List<Coin>`; если верхний JSON не список — понятное исключение. |
| `getCoinDetails(id)` | `/coins/{id}` с `localization=false`. Вернуть `CoinDetails`; если верхний JSON не объект — понятное исключение. |
| `getCoinsStream(ids)` | Через `async*` и `yield` загружать детали последовательно, в порядке id. Пустой список завершается без запросов. Первая ошибка завершает поток; следующие id не загружаются. |
| `pollPrices(ids, interval)` | `/coins/markets` с `vs_currency=usd`, `ids` через запятую и `per_page=250`. Первый запрос сразу после подписки. После ответа и отправки события выдержать `interval`, затем повторить. Запросы не перекрываются. `interval <= 0` — `ArgumentError`; пустой список — завершение без запросов. Ошибка завершает поток. Отмена прекращает новые запросы. |
| `getGrowingCoinNames(ids)` | Преобразовать `getCoinsStream`: `where` оставляет только `changePercent > 0`, `map` извлекает имя. `null`, ноль и отрицательные проценты пропускаются. Сохраняются порядок и ошибки. |
| `close()` | Закрыть переданный HTTP-клиент после завершения работы. |

Для polling: запрос → yield → пауза → следующий запрос. Запросы не перекрываются; interval отсчитывается после ответа. Первая ошибка завершает поток. После отмены не должно быть новых запросов, но уже начатый запрос или пауза могут завершиться позже. Поддерживаем до 250 id в одном polling-запросе.

В main уже включены все пять демонстраций через runDemo; каждый метод вывода находится ниже main. HTTP-клиент закрывается через repository.close() в finally.

## Основной сценарий: настоящий API

После реализации:

```bash
dart analyze
dart run lib/main.dart
```

Запросы выполняются **без токена**. Поддержку ключа или переменной окружения добавлять не нужно. Между двумя обновлениями цен — пауза 30 секунд. Возможны ограничения CoinGecko, HTTP 429/401/403 или недоступность сети.

## Запасной сценарий: тесты с моками

Если реальный API недоступен, требует ключ или ограничивает запросы, продолжайте работу и проверяйте решение локально:

```bash
dart test
dart test --name 'CLI без API' --reporter expanded
```

32 теста проверяют тот же контракт без CoinGecko, включая весь готовый вывод. Открывать тестовый файл не нужно. После установки зависимостей сеть для тестов не требуется. Ошибка внешнего API сама по себе не снижает оценку; обработка этой ошибки в вашем коде обязательна.

## Обработка ошибок — часть задания

- До разбора JSON проверьте HTTP status; при ошибке сообщите его код, например HTTP 429.
- Ограничьте ожидание ответа **15 секундами**. Обработайте таймаут и ошибку подключения.
- Повреждённый JSON и неверный верхний тип ответа должны приводить к понятному исключению.
- Не скрывайте ошибки пустым списком или фиктивным успехом. Передавайте их вызывающему коду; main уже выводит ошибку.
- Ошибки Stream/polling должны завершать поток и прекращать последующие запросы; close освобождает клиент.

Можно использовать стандартные Exception/FormatException/TimeoutException. Специальный класс исключения не требуется. Полная валидация каждого поля JSON не нужна.

## Критерии 0–2

- **0 баллов:** основная загрузка не реализована или решение не удаётся объяснить.
- **1 балл:** обе модели, запросы и последовательный Stream работают; **обработаны HTTP-ошибки, сеть, таймаут и неверный JSON**; проходят группы «Модели», «Запросы», «Stream»; студент объясняет await/yield.
- **2 балла:** дополнительно работают polling и where/map; **ошибки потоков передаются и останавливают дальнейшие запросы**, клиент закрывается; проходят все 32 теста и CLI; студент объясняет порядок и отмену. При доступном API покажите реальный запуск, при недоступном — вывод тестов и CLI на моках.

Сдать код, вывод проверок и короткое объяснение. Зелёные тесты без понимания не заменяют объяснение. Объявить критерии перед началом работы; к прошлым сдачам не применять.
